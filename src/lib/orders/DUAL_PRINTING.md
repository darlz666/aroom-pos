# Dual printing software acceptance

This phase adds two independent saved-order outputs. It does not establish
physical Bluetooth printer compatibility or authorize operational migrations.

## Cashier workflow

Enter an optional customer name before saving the order. Enable cup labels for
each beverage line that needs them and choose instructions separately for each
unit. Food and any line without that explicit choice produce no cup labels.
Each cup has sugar (NORMAL / LESS / NO SUGAR), ice (NORMAL / LESS / NO ICE), cup
(REGULAR / LARGE), and optional notes. Line notes remain available separately.

Options are preparation instructions. LARGE, reduced sugar/ice and notes do not
change prices or recipe consumption. Totals remain server-authoritative. Stock
is consumed once by the existing successful-payment transaction using product
recipe quantities. Confirm the intended product before accepting payment if a
different selling price or recipe is needed.

Unpaid editable orders can change customer, line notes and individual cups using
the existing expected revision and shift/payment checks. Increasing quantity
appends default cups; reducing quantity keeps the first remaining cups. Clearing
cup labels removes that line's preparation snapshots. Paid or cancelled metadata
cannot be edited. Historical products, prices and cup instructions are read from
saved snapshots, so menu changes cannot rewrite these outputs.

After successful payment, receipt and label previews use the existing authorized
paid-order read. Receipt and label simulations have separate actions and results;
each cup can be retried independently. A simulated result explicitly means that
no physical print occurred. A failed receipt does not fail a label and a failed
label does not change the receipt result. Completed jobs are terminal within the
open panel; an explicit historical copy is a separate job marked COPY.

Printing defaults to an unconfigured transport that fails clearly. Failed or
uncertain output must be inspected before a later retry: a future transport can
lose its acknowledgement after paper has already printed. Printing never changes
the saved order, payment or stock. Closing and reopening the browser does not
retain simulated results or prove that paper printed.

## Boundaries and stored data

- `orders/domain.ts` validates the customer, line notes and ordered per-unit
  details. Customer is at most 128 Unicode code points, line notes 500 and cup
  notes 300. Control characters and malformed Unicode are rejected.
- `Order.customerName` and `OrderItem.cupCustomizations` are nullable additions.
  Old orders require no backfill and yield no labels. Existing create-request
  fingerprints are unchanged when the new optional metadata is absent.
- Identical actor/key creation retries recover the saved order. Changing customer,
  notes, any cup option or unit order with the same key is a conflict.
- `printing/receipt-format.ts` renders a logical 58 mm receipt using saved integer
  rupiah values and Asia/Jakarta time. A 32-character text layout is a software
  convention, not a verified printer font/encoding specification.
- `printing/cup-label-format.ts` renders one logical label for each explicitly
  configured beverage unit. Label paper dimensions remain unset until the
  adhesive printer model and stock are confirmed.
- `PrinterAdapter` handles receipt output; `LabelPrinterAdapter` handles sticker
  output. Their destinations and job locks are separate. These interfaces are the
  integration boundary for a future Android transport.
- The explicit simulation adapters return `simulated`, never physical
  `succeeded`. No Bluetooth connection, permission prompt, printer bytes,
  operating-system pairing or device protocol is implemented here.
- Server authorization remains the existing POS receipt guard. Labels do not add
  an endpoint or grant STOCK_MANAGEMENT/FINANCE access to operational receipts.

## Verification and remaining hardware acceptance

Automated coverage includes normalization, historical fingerprints, independent
customizations, quantity resizing, persistent snapshots, duplicate creation,
revision/payment guards, database constraints, stock and payment isolation,
independent simulations, concurrency, failures, retries and copies.
`prisma/dual-printing.test.ts` accepts only an explicitly supplied local
`aroom_access_test_<32 hex characters>` URL, verifies actual database identity
before fixture writes and preserves unrelated rows. It never loads `.env`.
Use the isolated project verification runner; do not point this test at a real
application database.

Physical acceptance still requires the owner to identify the adhesive printer
model, command language, DPI, label size, gap/black-mark behavior, Unicode/font
support and cutting/feeding requirements. The EPPOS EP58M / RPP02N receipt printer
is confirmed as the intended 58 mm Bluetooth device, but its Android connection
and command behavior have not been tested in this software phase.

Test the chosen Android bridge/transport on the actual tablet with two distinct
paired destinations. Verify printer selection cannot cross receipt/label
destinations, paper widths, long names and notes, copies, disconnections,
acknowledgement loss, retries, failed permissions and printer state reporting.
Whether a browser can use either Bluetooth device remains unverified; a native
or other supported bridge must be selected and accepted before reporting physical
success. No deployment or operational migration is included in these steps.
